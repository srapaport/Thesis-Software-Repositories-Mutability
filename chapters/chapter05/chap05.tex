\chapter{Secret Removal in Version Control Archives}
\label{chap:secrets}

\section{Introduction}
\label{sec:sec-intro}

Chapter~\ref{chap:histories} ended with a specific gap left by the study of altered Git histories.
It showed that files whose names suggested secrets can be removed through history rewriting and still remain recoverable from Software Heritage at scale (\Cref{subsec:hist-sec-secrets}), but archival recovery alone cannot answer the security question that matters after a leak: whether the underlying credential is still valid and usable.
This chapter starts from the distinction established in \Cref{subsec:bg-secrets-remediation}: history rewriting acts on the repository record, while rotation---revoking the token, replacing the key, resetting the password---acts on the authority the leaked value grants, and only rotation invalidates the leak.

The problem is that developers sometimes perform only the optional repository cleanup and omit the required rotation.
An archive cannot observe that omission directly, but it can show whether the secrets that developers tried to remove remain recoverable.
If they do, and if even a fraction of them are still valid, the consequence is not merely an untidy Git history: valid secrets can open access to source repositories, deployment systems, cloud accounts, payment providers, messaging platforms, databases, or continuous-integration environments, depending on the credential family.
Platform-side scanning reduces this risk but is necessarily partial (\Cref{subsec:bg-secrets-detection}): it depends on the platform that receives the push, the detector coverage, the provider integration, and the credential type.
The result is a gap between repository-level deletion and credential-level remediation: the former can be observed in Git history, while the latter must be verified against the authority that accepts the credential.

This chapter addresses that gap empirically.
It does not yet claim to measure active secrets at ecosystem scale; the active-validation campaign remains unfinished and is constrained by responsible-disclosure requirements.
Instead, the chapter builds the measurement path needed to reach that result.
It first recovers and scans archived contents associated with secret-looking history alterations, establishing how many downloaded blobs contain machine-detectable secret patterns.
It then applies offline syntactic checks to the dominant private-key family and describes how further validity should be tested without invasive access: provider-assisted validation as the preferred path, and read-only checks run by the researcher only with explicit platform permission.
If secrets removed from history are still active often enough to matter, the evidence can support better platform protocols: faster provider notification, clearer distinction between cleanup and rotation, and remediation workflows that close the credential rather than only hiding the repository evidence.

\paragraph{What this chapter establishes.}
The chapter first describes the implemented detection and provenance pipeline (\Cref{sec:sec-methodology}), and then reports the current early detection results: the attrition from filename-filtered candidates to downloaded blobs, and the number of blobs with at least one scanner finding (\Cref{sec:sec-bearing-files}).
It then reports Tier~A offline validation for private keys and lays out the non-intrusive methodology that would turn the remaining findings into an active-credential study, before stating the threats to validity and the remaining work needed to complete the measurement (\Cref{sec:sec-validation,sec:sec-validity,sec:sec-conclusion}).

\section{Related Work}
\label{sec:sec-related}

Credential leakage in version control is a persistent and well-documented problem.
GitGuardian reported that exposed secrets in public GitHub repositories more than doubled between 2020 and 2021, exceeding six million disclosed credentials in a single year~\cite{segura2022secrets}.
Sinha et al. identified credential leakage in source-code repositories as an emerging security concern and argued that version control systems should incorporate automated mechanisms to prevent leaks and assist developers~\cite{DBLP:conf/msr/SinhaSDPM15}.
Meli et al. analysed a large sample of public GitHub repositories and recovered over \num{200000} API keys and tokens embedded directly in source code, showing that leakage is systematic rather than incidental~\cite{DBLP:conf/ndss/MeliMR19}.
The underlying weakness, hard-coded credentials, is catalogued as CWE-798 and recurs in the CWE Top~25 Most Dangerous Software Weaknesses, which places it among the most consequential classes of software defect.

Against this backdrop, the security community has converged on the remediation hierarchy summarised in \Cref{subsec:bg-secrets-remediation}: keep credentials out of source entirely, through environment variables and short-lived, automatically rotated credentials, and respond to a leak by rotating the affected credential~\cite{DBLP:conf/secdev/BasakNRW22, DBLP:journals/corr/abs-2211-06213}.
A gap remains between this guidance and observed developer behaviour: rewriting history is an immediately available and visible action that can be mistaken for remediation, yet the same commits persist in forks, cached mirrors, and version-control archives---a persistence Chapter~\ref{chap:histories} demonstrated at scale.
This chapter takes that recovery substrate as its starting point and asks the question those prior studies leave open: not how many secrets are exposed or removed, but how many of the secrets that developers tried to erase through history rewriting are still active.

\section{Study Design}
\label{sec:sec-methodology}

The central obstacle of this study seems to be scale.
Chapter~\ref{chap:histories} showed that history rewriting touches an enormous number of files: directory-level alterations alone account for \DIRRootCauseCommitsShort root-cause commits (\PercentDIRRootCauseCommits of all root-cause commits), of which \CategFileModifiedShort modify at least one file and \CategFileRemovedShort remove at least one.
Fetching the archived content of every such file and running secret detectors over all of it does not seem realistic to do in a reasonable amount of time; it would mean downloading and scanning on the order of hundreds of millions of files.
The study cannot yet inspect the content of everything, so it needs a way to decide what is worth retrieving \emph{before} any content is fetched.

The only information available at that point is the file path itself, its name and extension.
This is enough to form a useful guess, because credentials are far more likely to live in a file named like an SSH key, an environment file, or a cloud-credential file than in ordinary source code or an image.
The study therefore selects candidates by filename.
This is explicitly a heuristic: a promising name does not guarantee a secret, and an unusual name can hide one, so the filename stage only narrows the search and the real decision is deferred to a later content scan.

\subsection{Filename selection}

\paragraph{Choosing which filenames to keep.}
The candidate filenames are not chosen arbitrarily.
Pattern choice is informed by prior work on credential leakage~\cite{DBLP:conf/msr/SinhaSDPM15,DBLP:conf/ndss/MeliMR19} and by practitioner guidance on file types that most often carry secrets~\cite{segura2022secrets}.
Each pattern can be tagged with an evidence level that records how strong the justification is:
\begin{itemize}
    \item \textbf{E1} for an exact filename named in the literature;
    \item \textbf{E2} for an extension or file class named in the literature;
    \item \textbf{E3} for a naming convention inferred from E1/E2 evidence;
    \item \textbf{E4} for a practitioner-derived pattern not yet established in academic literature.
\end{itemize}

Selection proceeds in two filename passes, summarised in \Cref{tab:sec-filename-broad,tab:sec-filename-refined}.
The first pass casts a wide net over the altered-file corpus; the second pass keeps only the highest-signal basenames from that extraction.
Both passes decide on names alone; neither claims that a secret is present.

\paragraph{First pass: broad filename extraction.}
The first pass queries the altered-file corpus for paths whose basename matches a fixed list of names that suggested credentials, or whose path ends with a sensitive extension.
The exact basenames include environment and configuration files (\texttt{.env}, \texttt{web.config}, \texttt{config.yaml}), SSH and private-key names (\texttt{id\_rsa}, \texttt{id\_dsa}, \texttt{private.key}, \texttt{server.key}), key containers (\texttt{private.pem}, \texttt{keystore.p12}, \texttt{deploy.ppk}), and named credential files (\texttt{credentials.json}, \texttt{docker-compose.yml}); the full list, with evidence levels, is given in \Cref{tab:sec-filename-broad}.
This pass is intentionally high-recall: its purpose is to retain every plausibly secret-bearing path, not to decide that a secret is present.
It yields \SecretFirstExtractionShort (\SecretFirstExtraction) file records.

\paragraph{Narrowing to a workable set.}
Recovering and scanning \SecretFirstExtractionShort files does not seem tractable.
Each retained path must be resolved to archived content in Software Heritage, downloaded, deduplicated, and scanned with secret detectors; at that scale the pipeline would require hundreds of millions of archive lookups and blob downloads before any result could be reported.
The first pass therefore serves as an extraction step designed to maximise recall, not as the population analysed in this chapter.
A second pass narrows the \SecretFirstExtractionShort records to \SecretSecondExtractionShort (\SecretSecondExtraction) candidates by applying the basename regular expressions in \Cref{tab:sec-filename-refined}.
This removes the long tail of generic extensions admitted by the broad sweep---for instance, a generic \texttt{*.json} or \texttt{*.sh} file is dropped unless its basename also satisfies one of the refined patterns.
The reduction factor is roughly \num{128}:1; the detection results reported below are computed exclusively over this refined set.

\subsection{Secret detection}

\paragraph{Recovering and scanning content.}
For each remaining candidate, the corresponding archived file is recovered from Software Heritage, and identical copies are deduplicated so that content shared across many repositories is fetched only once.
The recovered files are scanned with scanned with gitleaks and TruffleHog, two widely used secret detectors~\cite{DBLP:conf/msr/BasakNRW23}.
Prior benchmarks show that their true-positive sets overlap only partially, so relying on either tool alone misses secrets the other finds~\cite{DBLP:conf/esem/BasakCRW23}.

Because the archive identifies a file by the fingerprint of its content rather than by its name, a detected secret must then be linked back to the places where that content appeared.
This last step is what turns a scanner hit into evidence about a specific repository, branch, and removed file, and it matters because one leaked file can resurface in many forks or rewritten histories.

The study works with three nested units.
A \emph{candidate location} is one altered file, identified by its repository revision and path, that the filename heuristic kept.
A \emph{content blob} is the deduplicated archived file recovered for one or more such locations.
A \emph{finding} is a secret matched by a detector inside a blob.

Linking a finding back to every location that shared the same blob recovers provenance, but it also means that, once expanded, the number of findings is larger than the number of distinct leaked files; the chapter keeps those counts separate to avoid confusion.

The filenames behind the findings confirm the same picture from the path side.
The most frequent gitleaks-flagged basenames are configuration and secret manifests, \texttt{secrets.yml} (\num{8471}), \texttt{config.yml} (\num{5433}), \texttt{.env} (\num{1604}), and \texttt{secrets.yaml} (\num{1424}), interleaved with explicit key and certificate files, \texttt{server.key} (\num{1098}), \texttt{config.json} (\num{851}), and \texttt{key.pem} (\num{724}).
Findings therefore cluster where developers conventionally place credentials: declared secret or configuration files and standalone key material.

These numbers answer only the detection part of the study.
They show that the archived contents of credential-looking paths from altered histories include scanner-detectable secrets.
They do not establish that any detected credential is authorised for a particular service or still active on a network.
For private keys, Tier~A offline checks (\Cref{sec:sec-pk-tier-a}) show how many flagged blobs contain cryptographically parseable key material; that syntactic filter is necessary but not sufficient for an active-rate claim.
The distinction between parseable and active credentials is central to the rest of the chapter, because the active-rate result remains unfinished.

\section{Non-Intrusive Validation and Responsible Disclosure}
\label{sec:sec-validation}

This study separates detection from validation.
Detection reports that a blob contains a pattern recognised by gitleaks or TruffleHog.
Validation asks whether the credential can still authenticate to a provider or service.
Validation is organised into three tiers so that the study can measure activity without treating third-party credentials as tools for unauthorised access.
Tier~A offline filtering has been executed for private keys (\Cref{sec:sec-pk-tier-a}).
As of July 2026, the Tier~B outreach message for the SSH-private-key family has been sent to GitHub's security team; Tier~B provider-assisted checks and Tier~C network checks run by the researcher have not yet been carried out, so no active-rate result is claimed while that response remains pending.

\begin{itemize}
\item \textbf{Tier A: offline validation.} Local structural or cryptographic checks issue no network traffic.
Examples include PEM extraction from literal text and from base64-encoded configuration values, followed by parsing with \texttt{ssh-keygen} and OpenSSL.
Tier~A can reject placeholders, truncated material, and misnamed files, but it cannot prove activity because a revoked credential can remain syntactically valid.
\item \textbf{Tier B: provider-assisted validation.} The researcher contacts the affected provider through an approved security channel and asks the provider to check the credentials on its side, revoke them where appropriate, and return only aggregate activity counts.
\item \textbf{Tier C: network validation run by the researcher.} The researcher performs a single read-only or metadata-only check only after explicit written provider authorisation for the precise command.
\end{itemize}

\subsection{Tier A results for private keys}
\label{sec:sec-pk-tier-a}

Private keys dominate the detection counts (\Cref{tab:sec-secret-types}), so they are the first family subjected to Tier~A filtering.
The check operates on unique content blobs, not on the path-level location counts of the detection tables: each of the distinct \texttt{sha1} values flagged as a private key by gitleaks or TruffleHog is validated once, regardless of how many repository paths reference it.
The implementation extracts PEM blocks from literal file text and from base64-decoded environment variables and YAML values, then attempts offline parsing with an empty passphrase.
No network calls are made.

Each blob receives one of five statuses.
A blob is \emph{valid} when at least one extracted PEM block parses successfully; \emph{encrypted} when key material is found but passphrase-protected (passphrases are not cracked); \emph{invalid} when text formatted like PEM is rejected by the parsers; and \emph{no\_blocks} when the scanner flagged the blob but the extractor found no PEM.
Throughout this subsection, \emph{valid} means cryptographically parseable offline, not enrolled on a hosting platform or otherwise usable on a network.

Because every TruffleHog private-key blob is also flagged by gitleaks, the TruffleHog row is a subset of the gitleaks row rather than an independent population.

Splitting the \num{11613} validated blobs by detector overlap clarifies where scanner noise concentrates.
Among the \num{9812} blobs flagged by both tools, \num{9444} (\SI{96.3}{\percent}) parse as valid offline.
Among the \num{1801} blobs flagged only by gitleaks, only \num{594} (\SI{33.0}{\percent}) parse as valid; gitleaks-only matches form the main false-positive pool at this stage.
TruffleHog therefore acts as a useful pre-filter for unparseable text that resembled key material, but relying on gitleaks alone would retain substantially more scanner noise in the Tier~A denominator.

Sixty-four blobs yielded valid keys only after base64 decoding from configuration lines (for example environment files or CI YAML), illustrating why literal PEM search alone would miss some genuine key material.
Encrypted blobs (\num{1091} under gitleaks) are syntactically plausible but cannot be parsed without a passphrase; they are excluded from any future active-check numerator.
The \num{10038} gitleaks-flagged blobs classified as valid offline form the syntactic denominator for a future Tier~B or Tier~C SSH-key activity study, subject to provider authorisation and responsible-disclosure constraints.
The corresponding outreach message has been sent to GitHub's security team, requesting either an aggregate provider-side check (Tier~B) or explicit written authorisation for a single read-only banner probe per key (Tier~C); no active-rate result is reported here because GitHub's response is still pending at the time of writing.

The study assigns one predefined check per credential family.
Each check is read-only or metadata-only, and the ``active'' outcome is fixed in advance.
The examples below illustrate the pattern; they are run only after Tier~A filtering and, for network checks, after provider authorisation (Tier~C).

\begin{itemize}
\item \textbf{SSH private key (GitHub).}\\
Offline: \texttt{ssh-keygen -y -f ./key} confirms syntactic validity (exit~0).\\
With authorisation, a single SSH banner probe:
\begin{verbatim}
ssh -i ./key -o IdentitiesOnly=yes -T git@github.com
\end{verbatim}
Active iff the banner contains \texttt{Hi <user>!}.

\item \textbf{GitHub personal access token.}
\begin{verbatim}
curl -H "Authorization: Bearer ghp_..." https://api.github.com/user
\end{verbatim}
Active iff HTTP~200.

\item \textbf{AWS access key.}
\begin{verbatim}
aws sts get-caller-identity
\end{verbatim}
Active iff HTTP~200 with an account ARN returned.

\item \textbf{OpenAI API key.}
\begin{verbatim}
curl -H "Authorization: Bearer sk-..." https://api.openai.com/v1/models
\end{verbatim}
Active iff HTTP~200.
\end{itemize}

These checks do not modify provider state nor use any premium API call of the leaker: they authenticate identity or list metadata.
The preferred path remains Tier~B, where the provider performs equivalent checks internally and returns only an aggregate count of credentials that appeared active.

The denominator for any future active-rate claim is therefore not the raw detector output.
It is the set of syntactically valid secrets that pass Tier A in a credential family for which Tier B or Tier C validation is authorised.
The numerator is the count of credentials confirmed active by the provider or by the authorised check.
When neither Tier B nor Tier C is available, active status is reported as unknown rather than inferred from silence.

The study would also excludes several families from active validation.
Generic certificate containers such as \texttt{*.pem}, \texttt{*.key}, \texttt{*.pfx}, and \texttt{*.p12} do not identify a target service by filename alone; if no subject alternative name points to a reachable host, they can only be reported as plausibly exposed.
Database credentials would also be excluded because probing private hosts through TCP authentication is more intrusive than a metadata-only provider request~\cite{yadmani2025}.
SSH keys without a Git-hosting target would also be excluded, because probing arbitrary hosts cannot be justified ethically.

The initial message asks a provider for a secure channel, states the credential family and count of syntactically valid credentials, and explicitly says that no live validation has yet occurred.
The preferred path is provider-assisted validation and revocation.
Silence is never treated as authorisation, and any active-rate result is reported conditional on provider authorisation, alongside the count and fraction of families excluded for lack of it.
Lack of response is not treated as authorisation.

\section{Threats to Validity}
\label{sec:sec-validity}

\subsection{Construct Validity}
\label{subsec:sec-val-construct}

The filename filter is intentionally high-recall, so many retained paths are configuration or credential-looking files without detector-visible secrets.
At the same time, it can miss secrets stored under unusual names.
Content recovery also removes data: only \num{2187481} of \num{2846017} candidate locations resolve to archived content, and \num{12} of \num{281740} unique blobs failed to download.
The detection result is consequently conditioned on successfully resolved and downloaded blobs.

gitleaks and TruffleHog use different detector rules and type taxonomies, so their secret-type labels are not directly comparable.
They can miss secrets outside their modeled formats, encoded or split credentials, and credentials that require repository context.
They can also flag non-secret high-entropy values or examples.
Tier~A offline validation has been applied to private keys (\Cref{sec:sec-pk-tier-a}) to reduce scanner noise before any active-rate denominator is formed for that family; other credential families remain unfiltered at this stage.
The type and extension composition reported in \Cref{tab:sec-ext-hitrate,tab:sec-secret-types} must be read with the same caution: it is shaped by the filename filter, which deliberately oversampled key-material names such as \texttt{.key}, \texttt{.pem}, and \texttt{id\_rsa}, so the dominance of private-key findings reflects selection bias as much as ecosystem prevalence, and the per-extension hit-rates are conditional on the candidate population rather than on all archived files.

\subsection{Conclusion Validity}
\label{subsec:sec-val-conclusion}

No active credential validation has been executed.
Tier~A offline filtering has been run for private keys: \num{10038} of \num{11613} flagged blobs parse as valid key material offline (\Cref{tab:sec-pk-tier-a}), but that syntactic result does not establish whether any key remains enrolled or usable.
The current detection and Tier~A results are therefore limited to archived content and offline parsing.
This chapter explains how to measure active credentials responsibly, and, for the SSH-private-key family, an outreach message has been sent to GitHub (\Cref{sec:sec-validation}); the repository does not yet contain a provider response, an authorised Tier~C run, or an aggregate active-rate output for this or any other family, since GitHub's answer remains pending at the time of writing.
Any statement about still-active secrets must therefore remain prospective until the Tier~B and Tier~C campaign exists.

When that campaign is carried out, any confirmed active count should be read as a lower bound rather than as a representative prevalence estimate.
The intuition here is that positive hits, if any, are likely to be few.
First, the archive snapshot is old relative to credential lifetimes.
The Software Heritage graph dataset underpinning both Chapter~\ref{chap:histories} and this chapter is frozen at \FullDataset.
A credential that appeared in an altered history years ago has had time to be revoked, rotated, or expired before this analysis begins.
Even the latest published Software Heritage release (March 2026) would leave a lag: at the time of writing (June 2026), a three-month interval is long enough that many token families may no longer be valid, because issuing platforms increasingly attach default expiration dates to API keys and similar credentials.
Second, the validation protocol prefers provider-assisted checks (\Cref{sec:sec-validation}), but many platforms are unlikely to reply to unsolicited security contact or to perform aggregate validation on behalf of a third-party study.
Families without Tier~B or Tier~C authorisation therefore remain in the unknown category, and a low or zero observed active count may reflect non-response as much as genuine revocation.

\section{Conclusion}
\label{sec:sec-conclusion}

This chapter reframed the secret-suppression case from Chapter~\ref{chap:histories} as a distinct, unfinished security study.
The implemented contribution is a pipeline that starts from credential-looking paths from altered histories, recovers their archived content in Software Heritage, scans the downloaded blobs with two secret detectors, and links findings back to their repository locations.
On the current run, \num{25859} of \num{281728} downloaded blobs have at least one detector finding, a blob-level rate of \SI{9.18}{\percent}.
Those findings are not spread evenly: they concentrate in private-key material and in a small set of high-yield file types (\texttt{id\_rsa}, \texttt{.key}, \texttt{.pem}, \texttt{.env}), while the broad configuration and source extensions contribute volume but few detections.
That result establishes that the archived contents of altered histories contain scanner-detectable secrets.
For private keys, Tier~A filtering further shows that \num{10038} of \num{11613} flagged blobs contain cryptographically parseable key material offline (\Cref{tab:sec-pk-tier-a}).
It does not establish whether those credentials remain active on any network.

\subsection{Perspectives}

Tier~A offline denominators are now available for private keys (\Cref{sec:sec-pk-tier-a}).
The next step is to extend the same structural filtering to the remaining credential families before any provider contact: parsing service-account JSON files, token formats, and connection strings where offline checks are possible.
The output of that step should not be an active-rate result.
It should be a family-by-family count of syntactically valid credentials, placeholders rejected, malformed findings, and families excluded from validation.
That denominator design matters because it prevents raw scanner output from being mistaken for confirmed credentials.

The second task is provider coordination for the Tier~B and Tier~C activity checks, following the process defined in \Cref{sec:sec-validation}.
This has started for the SSH-private-key family: GitHub has been contacted, and the corresponding active-rate result is pending their response.
The outreach logs must record dates, channels, follow-up status, closure status, and whether the provider authorised Tier B, authorised Tier C, declined, or did not respond; the future active-rate result should be reported only for authorised families, together with the number of syntactically valid credentials whose status remains unknown because no authorisation was obtained.
The same coordination step remains to be started for the other credential families identified in \Cref{tab:sec-secret-types} (service tokens and, where a reachable provider exists, other key-material families).

The final task is to answer the temporal and comparative questions that remain open.
The temporal question requires pairing the first exposure of a detected secret with the remediation attempt that removed it from the public history.
It would be interesting to know if quick remediation rhymes with no rotation, and more generally to observe if any correlation exists between a secret being active and the time it took to remove it from the public repository.
The comparative question requires comparing rotation or activity outcomes across secret families, but only after the validation campaign supplies active, revoked, and unknown outcomes.
Both analyses should keep the distinction between blobs, scanner findings, and expanded repository locations, because each denominator answers a different question.

The broader perspective is that secret removal exposes the limit of repository-level remediation.
The current evidence shows that history rewriting can remove a credential from the visible repository state while leaving the archived content available for later analysis.
The unfinished part is to measure how often this archival exposure remains operationally dangerous because the credential itself was not revoked and is still active.
Completing that measurement would turn the chapter from an early detection and offline-filtering study into a direct evaluation of whether developers and providers close the loop after secret exposure.
