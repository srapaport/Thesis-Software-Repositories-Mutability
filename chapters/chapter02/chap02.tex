\chapter{Background}
\label{chap:background}

\initial{T}his chapter introduces the technical concepts required to study mutability in public software repositories.
The thesis focuses on a tension that is easy to miss in ordinary Git usage: developers, package managers, build systems, and auditors often reason about repositories as if published states were stable~\cite{Vu21, torresarias2016gitmetadata}, while Git deliberately exposes mechanisms that allow references and histories to be rewritten~\cite[§2.4, Undoing Things]{ProGit2014}.
The empirical work in the thesis studies two manifestations of that mutability at scale: tag references used as release anchors that move or disappear while the tag name remains a familiar label~\cite{rapaport2026tagalterations}, and public commit graphs (commit histories) that change when history is rewritten and force-pushed, so previously resolved commit identifiers no longer describe the state reachable from a branch~\cite{DBLP:conf/kbse/RapaportPTZ25}.
This tension is not an implementation accident. It follows from the distinction between immutable content-addressed objects and mutable names that point to those objects.

The chapter first presents the Git object model and references, then mechanisms that rewrite history or retarget refs, and finally how those mechanisms interact with releases, supply chains, and archival observation.

\section{Git Repositories as Versioned Software Artifacts}
\label{sec:bg-git-repositories}

Git is a distributed version control system in which each clone contains a local copy of the repository history.
Developers usually create commits locally, share them by pushing to a public repository, and incorporate collaborators' work by pulling from that repository.
Public repositories therefore serve two roles at once: they are collaboration points for developers and source distribution points for downstream users, package managers, continuous integration systems, and researchers~\cite[§5, Distributed Git]{ProGit2014}.

This dual role is at the core of this thesis.
A repository can be manipulated as a local development workspace, where rewriting recent work is an accepted practice, while also being consumed as an external artifact, where stability is often expected.
%Understanding this tension requires first separating Git's immutable data model from its mutable naming layer.

\subsection{Commits, Trees, and Blobs}
\label{subsec:bg-commits-trees-blobs}

Git stores repository data in a content-addressable object store.
Objects are addressed by cryptographic digests (hashes) computed from their content and metadata, historically using SHA-1 and, in newer configurations, SHA-256~\cite{ProGit2014}.
The main object types relevant to this thesis are blobs, trees, commits, and annotated tags.
Blobs store file contents.
Trees describe directory structures by linking names to blobs and other trees.
Commits point to a source tree and to zero or more parent commits, and also contain metadata such as author, committer, timestamps, and commit message.

Because commit identifiers are computed recursively over commit content and metadata, a commit identifier refers not only to the source tree but also to its ancestry.
If any part of a commit changes, including a timestamp or message, the commit receives a new identifier.
If a later commit has the modified commit as an ancestor, that later commit also receives a new identifier because its parent link changed.
This recursive property forms a Merkle directed acyclic graph (DAG): the identity of a visible root commit can be used to verify the identities of all commits reachable from it (Figure~\ref{fig:bg-object-model}).

This model provides strong integrity properties at the object level.
Once a specific object identifier is known, one can verify that the object retrieved under that identifier has not changed.
However, the guarantee applies to objects, not to the human-readable names that users normally manipulate.
The distinction between object identity and reference identity is central to the mutability phenomena studied in this thesis.

\subsection{Branches, Tags, and References}
\label{subsec:bg-branches-tags-references}

Git users rarely interact directly with raw object identifiers (hashes).
They usually interact with references, or refs, which are names that point to objects.
Branches are refs under the \texttt{refs/heads/} namespace.
Tags are refs under the \texttt{refs/tags/} namespace.
Remote-tracking branches, pull-request refs, and other forge-specific names follow similar principles.

Branches are expected to move during development.
A branch such as \texttt{main} or \texttt{master} points to the latest commit considered part of that line of development, and each new accepted commit advances the branch.
This mutability is ordinary and visible: the purpose of a branch is to represent an evolving development line.

Tags have a different social role: they often mark particular repository states, especially software releases.
Release workflows frequently treat tag names as stable identifiers, although Git allows any tag ref to be deleted or retargeted; the consequences for downstream consumption are developed in \Cref{sec:bg-releases-provenance-reproducibility}.

Git supports two main kinds of tags.
A lightweight tag is a reference that points directly to another object, usually a commit.
An annotated tag is a distinct Git object containing metadata such as tagger identity, timestamp, and message; the tag ref points to that tag object, which in turn points to the release target.
Annotated tags therefore add a metadata layer, but they do not remove the mutability of the tag name.
The tag ref can still be updated to point to a different object, and the same visible tag name can later designate a different repository state.

This mutability is not incidental; it follows from Git's distributed design.
Centralized version control systems such as CVS and Subversion assign revision identifiers from a single authoritative server, so a given revision number denotes one canonical changeset across all clients.
In a distributed model, references are instead created independently in separate clones and must be reconciled when repositories synchronize: if two clones bind the same tag name to different commits, the protocol cannot preserve both bindings without violating name uniqueness.
Git therefore treats tags as mutable refs, prioritizing distributed flexibility over protocol-level immutability of release labels.
Platform-level mechanisms can partially compensate (\Cref{subsec:tags-disc-practical}), but they operate outside the core Git protocol and do not extend to plain Git operations or to other forges.

\subsection{Local and Remote Repository Synchronization}
\label{subsec:bg-local-remote-synchronization}

Git synchronization is built around exchanging objects and updating references.
When a developer pushes, the remote repository receives objects that it does not already have and updates one or more refs.
When another developer pulls, their local clone fetches the remote objects and updates local views of the corresponding remote refs.

In the common append-only case, synchronization is straightforward.
A branch advances from an old commit to a descendant commit; existing history remains reachable, and downstream clones can fast-forward.
The previous state is still present in the graph, and the new state extends it.

History rewriting breaks this simple model.
If a public branch is updated to point to a commit that is not a descendant of the previous branch tip, the remote ref has changed in a non-fast-forward way.
Downstream users who previously observed the old branch state may now hold commits that are no longer reachable from the public branch.
Users who clone after the rewrite may never see those commits at all.
Figure~\ref{fig:bg-sync-rewrite} contrasts the append-only and rewritten cases.
This is the practical setting in which repository mutability becomes observable and consequential.

\section{Mutability in Git}
\label{sec:bg-mutability-git}

The object--reference distinction above supports local experimentation, branch movement, and release correction, but creates ambiguity when mutable names are treated as stable identifiers.
The contributions on altered histories and tag alterations study two observable forms of that ambiguity: changes to the commit graph reachable from public branches, and changes to tag refs used as release anchors.

\subsection{History Rewriting Mechanisms}
\label{subsec:bg-history-rewriting}

Git provides several mechanisms for rewriting recorded history.
The \texttt{commit --amend} operation creates a replacement for a recent commit, often to modify the commit message, adjust metadata, or add forgotten file changes; \Cref{lst:commit-amend-message} illustrates correcting a typo in the most recent commit message.
Rebase operations replay, reorder, squash, split, or otherwise transform a sequence of commits.
These operations are common in local or work-in-progress development because they help developers prepare a cleaner sequence of commits before sharing it.

\begin{lstlisting}[
  style=thesisbash,
  caption={Correcting a typo in the latest commit message with \texttt{git commit --amend}.},
  label={lst:commit-amend-message},
]
# The latest commit message contains a typo ("authentcation").
$ git commit --amend -m "Fix authentication logic"
[main 7f3a1c2] Fix authentication logic
 Date: Mon Jun 1 10:00:00 2025 +0200
 1 file changed, 0 insertions(+), 0 deletions(-)
$ git push --force
 Enumerating objects: ...
 [...]
 To github.com:something.git
  + 9fddc2f...7f3a1c2 main -> main (forced update)
\end{lstlisting}

At the object level, rewriting does not mutate an existing commit object in place.
Instead, Git creates new commit objects.
The old commits remain in object storage as long as they are retained locally or by another archive, but they may become unreachable from the public refs of the repository.
Because commit identifiers cover parent links, a direct change to one commit can propagate to descendants: later commits that point to the modified commit must also be replaced by new commits.
The thesis describes this phenomenon as a snowball effect, where one direct modification can cause many reachable commit identifiers to disappear from a later public snapshot (Figure~\ref{fig:bg-snowball-effect}).

History rewriting is therefore not inherently suspicious.
It is a normal part of some development workflows, particularly for pull-request branches and automated maintenance branches.
It becomes problematic when performed on public branches consumed as external artifacts (\Cref{sec:bg-git-repositories}), where rewrites can invalidate previously observed commit identifiers and complicate audit trails.

\subsection{Force Pushes and Reference Updates}
\label{subsec:bg-force-pushes-reference-updates}

Public history rewriting is usually made visible through reference updates.
A remote repository may reject non-fast-forward updates by default, but maintainers can often override this protection through force pushes or platform-specific settings.
A force push changes the public ref to point to a new commit even when that commit does not extend the previous public history.

The same principle applies to tags (\Cref{subsec:bg-branches-tags-references}).
Tag deletion, recreation, and force-update are often legitimate, for example when correcting a release mistake or cleaning a repository.
Git's own documentation nonetheless discourages reusing a published tag name: the \texttt{git-tag} manual recommends issuing a new version label (for example, ``X.1'') rather than force-updating ``X'', because two clones may then both claim ``version X'' while resolving to different commits, and Linus Torvalds argued as early as 2007 that silently overwriting an already fetched tag is a security problem that maintainers must announce explicitly rather than perform quietly~\cite{git_tag_retagging_docs,torvalds_retagging_2007}.
The security and reproducibility issue is therefore not that such operations are always malicious, but that the practice runs against documented guidance and that downstream tools may not record enough information to detect its consequences.

For this thesis, a tag alteration is an observable change in the state of a tag across repository snapshots.
The tag-alterations contribution distinguishes two main cases.
A tag move occurs when a tag is observed before and after an alteration but resolves to a different target, including deletion followed by later recreation with a different target.
A tag deletion occurs when a previously observed tag disappears from a later snapshot.
Moves and deletions differ in observability: a deletion breaks resolution, whereas a move preserves the tag name while changing the retrieved object (Figure~\ref{fig:bg-tag-alteration-types}; \Cref{subsec:bg-stable-references-dependency-resolution}).

\subsection{Apparent Immutability and Practical Mutability}
\label{subsec:bg-apparent-immutability}

Object identifiers are stable under Git's content-addressed model; ref names are not (\Cref{subsec:bg-commits-trees-blobs,subsec:bg-branches-tags-references}).
The resulting risk is therefore semantic as much as technical.
Developers and tools assign meanings to references: a branch is usually understood as moving, while a release tag is often understood as stable, yet Git enforces neither convention.
When social expectations about references diverge from the guarantees provided by the version control system, downstream users can make reproducibility and integrity assumptions that the system does not satisfy.
Figure~\ref{fig:bg-object-ref-layers} summarises the two-layer model.
How dependency specifications and build tooling translate that gap into concrete failures is examined in \Cref{sec:bg-releases-provenance-reproducibility}.

\section{Releases, Provenance, and Reproducibility}
\label{sec:bg-releases-provenance-reproducibility}

Software releases connect repository history to downstream consumption.
They provide names, version numbers, source archives, build inputs, and provenance claims.
In a reproducibility context, the key question is whether a recorded release reference continues to identify the same source artifact over time.

\subsection{Tags as Release Identifiers}
\label{subsec:bg-tags-release-identifiers}

Tags are widely used to mark releases because they provide stable-looking, human-readable names for repository states.
Project documentation, dependency files, package recipes, and continuous integration workflows can refer to tags instead of raw commit hashes, which aligns with common versioning practices where names such as \texttt{v2.3.1} denote release versions rather than arbitrary commits.
\NOTEside{citation}

Recording only a tag name fixes a mutable ref, not an immutable source identity (\Cref{subsec:bg-apparent-immutability}).
The tag-alterations contribution frames the resulting gap as a structural mismatch between practices that treat tag names as stable release identifiers and Git semantics that allow reassignment or removal, developed in \Cref{subsec:tags-stability-assumptions}.
This mismatch matters especially for computational research workflows and package ecosystems, where later rebuilds depend on recovering the same source state.

\subsection{Stable References and Downstream Dependency Resolution}
\label{subsec:bg-stable-references-dependency-resolution}

Downstream tooling consumes repository references in many ways.
Package ecosystems and build systems translate repository states into consumable artifacts: they may fetch source archives from forges, clone repositories, resolve tags, apply patches, check integrity metadata, and produce binary packages.
The reliability of that pipeline depends on assumptions about the upstream references recorded as inputs.
Some package ecosystems support direct dependencies on Git repositories.
Build scripts may fetch source archives generated from tag names.
Continuous integration workflows may use third-party actions or tools by specifying a tag.
In all these cases, the repository reference becomes part of a larger software supply chain.
\NOTEside{Citation}

If a dependency specification records a commit identifier, the source identity is stable as long as the object remains available.
If it records a tag name, stability and integrity depend on whether the tag is preserved, deleted, or moved.
A deleted tag can cause a fetch failure.
A moved tag can cause the fetch to succeed while producing a different source state.
The second case is more subtle because the dependency name still resolves.
Figure~\ref{fig:bg-dependency-resolution} summarises these downstream outcomes.

This distinction is visible in package managers that record integrity metadata.
Nix, for example, stores expected hashes for fixed-output sources.
If a tag later resolves to different content, the build does not silently accept the new source; it fails with a hash mismatch.
This behavior avoids silent substitution, but it also shows that tag mutability can become an availability and rebuildability problem.
A package that was reproducible while a cached source artifact was available may become unrebuildable later if rebuilding requires fetching an upstream tag that no longer matches the recorded hash.
The tag-alterations contribution demonstrates this relationship empirically through a cross-analysis with Nixpkgs (\Cref{subsec:tags-reproducibility}).

\subsection{Implications for Reproducible Builds}
\label{subsec:bg-provenance-reproducible-builds}

Reproducible builds aim to increase confidence that generated binaries correspond to auditable source code~\cite{DBLP:journals/software/LambZ22}.
That goal depends on stable identification of build inputs, not only on deterministic build processes: if an input is named by a mutable ref, a deterministic process may still fail to reproduce the same artifact because the resolved source tree has changed.
Build-relevant resolution therefore requires pinning to a commit hash or to an independently archived persistent identifier~\cite{cise-2020-doi}; human-readable release names remain useful for communication but do not by themselves establish provenance.

\section{Software Repositories in the Software Supply Chain}
\label{sec:bg-software-supply-chain}

Software repositories are not only development workspaces.
They are upstream nodes in dependency networks, build systems, package ecosystems, deployment pipelines, and research artifacts.
A change in repository state can therefore affect actors who are not repository maintainers and who may not observe the change directly.

\subsection{Repositories as Sources of Code and Metadata}
\label{subsec:bg-repositories-code-metadata}

A Git repository contains more than source files.
It contains commit metadata, branch structure, tag names, annotated tag objects, release conventions, and sometimes platform-managed metadata.
Commit messages and authorship metadata help auditors understand why changes were made.
Branch names suggest development status.
Tags identify releases.
License files and documentation inform downstream usage.

History alterations and tag alterations can affect different layers of this information.
A history rewrite may change file contents, remove files, alter commit metadata, or move content to a different branch.
A tag alteration may change the source tree behind a release name, change only commit identity, change only the tag or release layer, or delete the release reference entirely.
The empirical contributions use taxonomies to separate these cases because they have different implications.

This layered view is important for supply-chain analysis.
A change that only modifies a commit timestamp does not have the same effect as a change that removes a secret, changes a license file, or retargets a release tag to different source code.
At the same time, even metadata-only changes can matter for auditability because they alter the identifiers and evidence that downstream users rely on.

\subsection{Relationships with Package Ecosystems and Build Systems}
\label{subsec:bg-package-ecosystems-build-systems}

Tag mutability in package recipes and build inputs is examined in \Cref{subsec:bg-stable-references-dependency-resolution}.
The altered-histories contribution highlights a complementary issue for repository users and auditors.
Rewritten histories may go unnoticed by users who perform fresh clones, because they see only the current public state.
Users who previously cloned the repository may detect disruption when pulling, but many automated workflows do not preserve such state.
As a result, repository history can change in ways that are difficult for downstream systems to observe unless they rely on external archives or dedicated monitoring tools.

\subsection{Trust Dependencies Across the Software Supply Chain}
\label{subsec:bg-trust-dependencies}

Open-source software supply chains involve implicit trust relationships among maintainers, forges, package managers, build systems, and users.
Prior work on supply-chain attacks emphasizes that dependency resolution and externally controlled infrastructure are recurring sources of risk~\cite{ladisa2023supplychain}; repository mutability adds another channel because a dependency name can resolve to different source code over time.

Not every history rewrite or tag alteration is malicious---many are local cleanup, pull-request maintenance, bot-driven updates, or release corrections.
The background issue is narrower: when downstream actors treat Git refs as stable artifact identities, benign maintenance, reproducibility failures, and attack opportunities can overlap.

This thesis therefore treats repository mutability as a supply-chain integrity problem when three conditions coincide.
First, a public reference or history state is consumed by downstream users.
Second, those users rely on the stability or auditability of that state.
Third, later repository changes invalidate that reliance by making previous source states inaccessible, ambiguous, or indistinguishable from altered ones without external evidence.

\section{Secrets in Source Code Repositories}
\label{sec:bg-secrets}

Public repositories distribute source code to collaborators, package managers, continuous integration systems, and downstream users (\Cref{sec:bg-git-repositories}).
That distribution model assumes the published tree is safe to inspect, clone, and reuse.
When authentication material is committed by mistake, the repository becomes an accidental channel for credential exposure.
In this thesis, a \emph{secret} denotes any credential or key material whose disclosure would grant access to a protected resource: API tokens, passwords, database connection strings, private keys, certificates, and similar values that should remain outside version control.

The weakness is well known in software security practice.
Hard-coded credentials are catalogued as CWE-798 and recur among the most consequential classes of software defect.
Empirical work on public GitHub repositories shows that leakage is systematic rather than anecdotal: Meli et al.\ recovered more than \num{200}\,k API keys and tokens embedded directly in source code~\cite{DBLP:conf/ndss/MeliMR19}, and industry monitoring reports describe millions of exposed credentials in public repositories in a single year~\cite{segura2022secrets}.
Sinha et al.\ argued early that version control systems should incorporate automated mechanisms to prevent such leaks and to assist developers after exposure~\cite{DBLP:conf/msr/SinhaSDPM15}.
Because public repositories are copied, forked, indexed, and archived, a single push can propagate sensitive values far beyond the maintainer's immediate workspace.

\subsection{Detection and Prevention}
\label{subsec:bg-secrets-detection}

Two complementary lines of defence address credential exposure in repositories.
The first is \emph{detection}: scanning repository contents for patterns that resemble known secret formats.
Open-source tools such as gitleaks and TruffleHog implement large rule sets over file contents; benchmark studies show that their reported findings overlap only partially, so no single detector captures the full set of machine-recognisable secrets~\cite{DBLP:conf/msr/BasakNRW23,DBLP:conf/esem/BasakCRW23}.
The second is \emph{prevention at the forge}: hosting platforms can scan pushes, warn maintainers, notify credential providers, or block known-dangerous formats before they become part of the public history.
GitHub, for example, rejects pushes that contain certain private-key formats and operates secret-scanning partnerships with major providers.

These mechanisms reduce risk but do not eliminate it.
Detector coverage depends on the rule set, the file types scanned, and whether credentials are split, encoded, or stored under unusual paths.
Platform scanning applies only to the forge that receives the push and to the credential families for which an integration exists.
Private keys for self-hosted services, database passwords, certificates, and values copied into archives or mirrors may fall outside the cleanest version of this model.
Filename heuristics---matching paths such as \texttt{.env}, \texttt{id\_rsa}, or \texttt{credentials.json}---are therefore widely used in practice as a coarse first filter before content scanning, including in the empirical work of this thesis (\Cref{chap:histories,chap:secrets}).

\subsection{Recommended Remediation}
\label{subsec:bg-secrets-remediation}

Surveys of secret-management practice converge on a clear hierarchy.
Credentials should be kept out of source entirely, through environment variables, secret managers, and short-lived tokens that can be rotated without rewriting history~\cite{DBLP:conf/secdev/BasakNRW22,DBLP:journals/corr/abs-2211-06213}.
When exposure occurs despite these precautions, the security remediation is to invalidate the leaked value: revoke the token, replace the key, reset the password, or otherwise remove the authority that the exposed string grants.
Krause et al.\ study how developers prevent and respond to accidental commits; their findings reinforce that rotation, not deletion from the repository alone, closes the security gap~\cite{DBLP:journals/corr/abs-2211-06213}.

History rewriting is nonetheless a common \emph{cleanup} action after a leak.
Maintainers can amend or rebase recent commits, run history-filtering tools over past trees, and force-push the rewritten branch so that the current public view no longer contains the offending file (\Cref{subsec:bg-history-rewriting,subsec:bg-force-pushes-reference-updates}).
This action can reduce the chance that a future clone or casual inspection rediscovers the value, and it may satisfy organisational policy about what may remain in advertised project history.
It does not, however, act on the credential itself.
Nor does it erase every copy of the exposed commits: forks, local clones, search indexes, and independent archives may retain the pre-rewrite state long after the upstream repository looks clean (\Cref{sec:bg-software-heritage}).
The distinction between repository-level cleanup and credential-level remediation is central to the secret-removal thread of this thesis.
Chapter~\ref{chap:histories} shows that files whose names suggested secrets and that were removed through history rewriting remain recoverable from Software Heritage at scale; Chapter~\ref{chap:secrets} asks whether the recovered values are still valid credentials.

\section{Software Heritage and Archival Observation}
\label{sec:bg-software-heritage}

The empirical contributions rely on an archival view of public repositories because, after a ref update or history rewrite, the previous public state may no longer be available from the original forge (\Cref{sec:bg-mutability-git}).
Without an independent archive, the evidence needed to compare before and after states may have disappeared.

Software Heritage is a universal archive of publicly available source code~\cite{swhcacm2018,swh-msr-2020-challenge}.
It periodically visits software origins, such as repository URLs, and stores observed repository states as snapshots.
For Git repositories, a snapshot records visible references and the archived objects designated by those references.
Software Heritage stores these artifacts in a global Merkle DAG and assigns persistent identifiers (SWHIDs) to archived objects, including revisions (similar to commits in Git's architecture), directories, releases, and snapshots~\cite{cise-2020-doi}.

This archival model makes repository mutability observable.
In the altered-histories contribution, consecutive snapshots of the same origin are compared to detect commits that were reachable in an earlier snapshot but missing from a later one.
In the tag-alterations contribution, consecutive snapshots are compared to detect tag moves and deletions.
In both cases, the archive preserves evidence of states that may no longer be visible in the current upstream repository (Figure~\ref{fig:bg-swh-snapshots}).

The archival view also imposes limits.
It can only observe alterations that occur between visits and remain visible long enough to be captured.
If a reference is changed and restored between two archival visits, the alteration may be missed.
If several changes happen between two visits, they may be observed as one aggregate transition.
Counts derived from such snapshots should therefore be interpreted as lower bounds on observable alterations, not as complete records of every repository event.

\section{Terminology and Conceptual Scope}
\label{sec:bg-terminology-scope}

This section fixes the main terms used throughout the thesis.
The definitions are intentionally tied to observable repository states because the empirical contributions rely on archived snapshots rather than on privileged forge logs or maintainer intent.

\subsection{Mutable Releases}
\label{subsec:bg-mutable-releases}

A \emph{mutable release} is a release-like repository reference whose visible name remains usable as a release identifier while the object it designates can change or disappear; in this thesis, the primary example is a Git tag (\Cref{subsec:bg-branches-tags-references,subsec:bg-tags-release-identifiers}).
The term does not imply malicious intent---correction, cleanup, migration, and platform convention all produce mutable releases---but it becomes security- or reproducibility-relevant when downstream users expect the identifier to designate a stable source state.

\subsection{Altered Histories}
\label{subsec:bg-altered-histories}

An altered history is an observable change in the commit graph reachable from a repository reference between two snapshots.
Following the altered-histories contribution, a repository undergoes a history alteration when at least one commit reachable from an earlier snapshot is missing from a later snapshot of the same repository.
An altered commit is a commit that was present in the earlier snapshot and absent from the later one.
Because of the snowball effect (\Cref{fig:bg-snowball-effect}), a single history alteration can yield many altered commits; for each alteration, the empirical chapters identify one or more \emph{root-cause commits}: the oldest commits, in topological order, among all altered commits---those directly altered rather than changed as a consequence of an earlier modification.

This definition captures observable effects, not developer intent.
It does not by itself determine whether the alteration was caused by rebasing, amendment, branch deletion, repository cleanup, or malicious tampering.
Additional classification is required to describe what changed and what risks follow from it.

\subsection{Secret Removal}
\label{subsec:bg-secret-removal}

\emph{Secret removal} denotes attempts to remove sensitive information from repository history after it has been committed, typically by rewriting history and force-pushing so that credential-looking files no longer appear in the public commit graph (\Cref{subsec:bg-secrets-remediation,subsec:bg-altered-histories}).
The term describes an observable repository operation, not the security outcome of that operation.
A successful rewrite can make a secret invisible in the current upstream tree while the underlying credential remains valid, and an unsuccessful one---from a security standpoint---can leave both the repository evidence and the credential active.

The altered-histories contribution treats secret removal as a case study within the broader taxonomy of history alterations.
It identifies removed files whose names commonly denote private information, such as private keys, certificates, or password stores, and shows that such removals are frequent enough to be a first-order phenomenon rather than an edge case (\Cref{subsec:hist-sec-secrets}).
That study establishes prevalence and recoverability at the filename level; it does not determine whether recovered contents still grant access.
Chapter~\ref{chap:secrets} extends the thread by recovering archived contents for credential-looking removals, scanning them with secret detectors, and defining a non-intrusive protocol for testing whether detected values remain active.
Together, these chapters separate three questions that are often conflated in practice: whether developers attempt to erase secrets from public history, whether those secrets remain recoverable from archives, and whether the recovered credentials still work.
