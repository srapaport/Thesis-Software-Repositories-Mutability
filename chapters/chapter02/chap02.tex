\chapter{Background}
\label{chap:background}

\initial{M}odern software is assembled rather than written from scratch: each software can draw on hundreds or thousands of upstream components, each maintained in their own public repository and consumed through package managers, build systems, and continuous integration~\cite{ladisa2023supplychain}.
Working on a single project, it is easy to overlook how that project sits inside a much larger ecosystem of producers and consumers.
This chapter is a tour of that ecosystem.
We begin at the scale of the whole software supply chain and move step by step toward the specific mechanisms that store, distribute, and preserve source code.

\section{The Software Supply Chain and Software Repositories}
\label{sec:bg-software-supply-chain}

The \emph{software supply chain} is the set of people, processes, and infrastructure that turn source code into software people actually run.
Figure~\ref{fig:bg-supply-chain-overview} sketches the main actors and flows at a high level.
A typical software is assembled from many upstream components---libraries, tools, and frameworks that other teams publish and maintain.
Each of those components is usually distributed as a \emph{package}: a named bundle of source code (or binaries) that a project declares as a dependency.
Packages are identified by \emph{versions}---labels such as \texttt{2.3.1} that tell a build (assembling a software from its own source and its declared dependencies and producing an artifact ready to use) which release of a component to use, so that the same declaration can be understood across machines and over time in a readable way that appears to look chronological.

Downstream projects rarely fetch those dependencies by hand.
They rely on \emph{package managers}: tools that download the right package from the registry for each declared version and wire it into the build.
npm (for JavaScript), PyPI (for Python), crates.io (for Rust), and Maven Central (for Java) are among the most widely used; together they resolve version specifications for millions of developers every day, usually by consulting the upstream projects where each package is maintained.

Once dependencies are declared, teams need to know that a build still works when code changes.
\emph{Continuous integration} (CI) pipelines automate that check: on each change, they install the declared dependencies, compile or test the project, and report failure before broken code reaches users.
On GitHub, CI is commonly run through \emph{GitHub Actions}: reusable workflow steps, packaged as \emph{actions}, that one repository can invoke in its own pipeline by name or version tag.
Many projects also keep a \emph{lockfile}---a machine-generated record of the exact sources retrieved during a successful build---or a \emph{software bill of materials} (SBOM), an inventory of every component that went into that build, so that the same inputs can be recovered later for auditing or reproduction.
Provenance frameworks such as Supply-chain Levels for Software Artifacts (SLSA) attach further metadata documenting where those inputs came from~\cite{tamanna2024analyzingchallengesdeploymentslsa}.
All of these mechanisms share one premise: that resolving a dependency specification today yields the same artifact as resolving it yesterday.

The upstream projects where package managers look for source code are stored in \emph{software repositories}: places where code is kept, versioned, and shared.
Git is a distributed version control system in which each clone contains a local copy of the repository history.
Developers usually create commits locally, share them by pushing to a public repository, and incorporate collaborators' work by pulling from that repository.
Public repositories therefore serve two roles at once (Figure~\ref{fig:bg-supply-chain-overview}): they are collaboration points for developers and source distribution points for downstream users, package managers, continuous integration systems, and researchers~\cite[§5, Distributed Git]{ProGit2014}.
This dual role is at the core of this thesis.
A repository can be manipulated as a local development workspace, where rewriting recent work is an accepted practice, while also being consumed as an external artifact, where stability is often expected.

A Git repository contains more than source files.
It contains commit metadata, branch structure, tag names, annotated tag objects, release conventions, and sometimes platform-managed metadata.
Commit messages and authorship metadata help auditors understand why changes were made.
Branch names suggest development status.
Tags identify releases or set a specific state of a repository in stone.
License files and documentation inform downstream usage.
Because all of this information is consumed by actors who are not repository maintainers and who may not observe a change directly, a repository functions as a \emph{trust anchor} for the supply chain: downstream systems treat the names it publishes as if they were durable identifiers, even though, as the rest of this chapter shows, the version control system enforces no such durability.

\section{Supply-Chain Attacks and the Repository Attack Surface}
\label{sec:bg-supply-chain-attacks}

A \emph{software supply-chain attack} compromises downstream users not by exploiting a vulnerability in their own code, but by manipulating an upstream component they depend on.
Consumers would then execute or ship attacker-controlled artifacts through their normal build and update process~\cite{ladisa2023supplychain}.
Prior work emphasizes that dependency resolution and externally controlled infrastructure are recurring sources of risk; repository \emph{mutability} (the capacity of a published name or state to change over time) adds another channel, because a dependency name can resolve to different source code over time.

In March 2025, attackers retargeted the version tags of \texttt{tj-actions/changed-files}, a widely reused GitHub Actions helper, so that hundreds of existing version labels all pointed to a single malicious commit; any pipeline that invoked the action by a pinned version string then executed attacker code on its next run, dumping CI secrets into workflow logs~\cite{paloalto_unit42_2025}.
The attack required no software vulnerability: its leverage came entirely from the gap between what Git's reference model permits and what downstream consumers assume.

A \emph{repository's attack surface} is the comprehensive collection of entry points where attackers can inject malicious code into an open-source project.
Because modern software development is highly distributed, this surface is vast and has both technical and social facets.

The technical surface includes the Version Control Systems, the build systems compiling the source code, and the distribution platforms where package managers download the final artifacts.
The personal workstations of the project maintainers and system administrators are also critical technical targets.

The social surface involves the people interacting with these systems: the contributors, maintainers, administrators, and downstream users.
Attackers frequently exploit the inherent trust between these distributed actors.
Rather than breaking a server's encryption, an attacker might compromise a maintainer's account, use social engineering, or submit a malicious code commit disguised as a legitimate bug fix.

Ultimately, this attack surface spans the entire end-to-end software supply chain.
Securing it requires protecting not just the final SBOM or the source code, but every intermediate system and every human participant involved in the software's lifecycle.

The \emph{repository's attack surface} is too vast to be treated in its entirety, only a small portion of it will be relevant in this thesis: the mutability of the names and states a repository publishes.
\label{subsec:bg-trust-dependencies}%
This thesis treats such mutability as a supply-chain integrity problem when three conditions coincide: a public reference or history state is consumed by downstream users; those users rely on its stability or auditability; and a later repository change invalidates that reliance by making previous source states inaccessible, ambiguous, or indistinguishable from altered ones without external evidence.
Studying this portion is a deliberate choice rather than a claim of completeness---compromised maintainer accounts, malicious contributions, and build-system attacks are equally real, but they require different observational instruments than the archival data this thesis builds on.

\section{Git and the Git Object Model}
\label{sec:bg-git-model}

Git is one of the most widely deployed distributed version control systems~\cite{DBLP:journals/access/GrilliS24, ProGit2014, DBLP:conf/ndss/HoltgraveFFHBKF25}, and it is also the format in which development history is stored on the forges and package sources through which most upstream open-source components are published~\cite{DBLP:conf/msr/PietriSZ20}.
Git stores repository data so that integrity is a property of content rather than of names.
In this section I introduce the object model and references that the rest of the thesis relies on.

\subsection{Commits, Trees, and Blobs}
\label{subsec:bg-commits-trees-blobs}

Git stores repository data in a content-addressable object store.
Each object is named by an \emph{identifier}: a cryptographic digest (hash) computed from its content and metadata, historically using SHA-1 and, in newer configurations, SHA-256~\cite{ProGit2014}.
The identifier is therefore a fingerprint of the object: retrieving an object under a given hash and recomputing the digest must yield the same value, or the content has been altered.
Finding a different object that hashes to an already published identifier requires brute-forcing a space of roughly $2^{160}$ possibilities for SHA-1 and $2^{256}$ for SHA-256, which is computationally infeasible with current hardware; collision attacks against SHA-1 exist for adversarially crafted inputs, but substituting arbitrary Git objects while preserving a target hash remains impractical in ordinary threat models.
The main object types relevant to this thesis are blobs, trees, commits, and annotated tags.
Blobs store file contents.
Trees describe directory structures by linking names to blobs and other trees.
Commits point to a source tree and to zero or more parent commits, and also contain metadata such as author, committer, timestamps, and commit message.

Because a commit's identifier is computed  recursively over its content, metadata, and the identifiers of its parents, it refers not only to the source tree but also to its ancestry.
If any part of a commit changes, including a timestamp or message, the commit receives a new identifier.
If a later commit has the modified commit as an ancestor, that later commit also receives a new identifier because its parent link changed.
This recursive property forms a \emph{Merkle directed acyclic graph} (DAG): a graph of objects with no cycles in which each node's identifier refers to its own content and to the identifiers of its parents.
The identity of a visible commit can therefore be used to verify the identities of all commits reachable from it: any tampering anywhere in the ancestry would propagate to a different hash (Figure~\ref{fig:bg-object-model}).

This model provides strong integrity properties at the object level: identifiers are \emph{immutable} in the sense that an object's content and metadata cannot change without changing its hash.
Once a specific object identifier is known, one can verify that the object retrieved under that identifier has not changed by recomputing the digest.
However, the guarantee applies to objects, not to the human-readable names that users normally manipulate.

\subsection{Branches, Tags, and References}
\label{subsec:bg-branches-tags-references}

Git users rarely interact directly with raw object identifiers (hashes).
They usually interact with references, or refs, which are names that point to objects.
Branches are refs under the \texttt{refs/heads/} namespace.
Tags are refs under the \texttt{refs/tags/} namespace.

Branches are expected to move during development.
A branch such as \texttt{main} or \texttt{master} points to the latest commit considered part of that line of development, and each new accepted commit advances the branch.
This mutability is ordinary and visible: the purpose of a branch is to represent an evolving development line.

Tags have a different social role: they often mark particular repository states, especially software releases.
Release workflows frequently treat tag names as stable identifiers, although Git allows any tag ref to be deleted or retargeted.

Git supports two main kinds of tags.
A lightweight tag is a reference that points directly to another object, usually a commit.
An annotated tag is a reference associated to a distinct Git object containing metadata such as tagger identity, timestamp, and message; the tag ref points to that associated object, which in turn points to the release target.
Annotated tags therefore add a metadata layer, but they do not remove the mutability of the tag name.
The tag ref can still be updated to point to a different object, and the same visible tag name can later designate a different repository state.

This mutability is not incidental; it follows from Git's distributed design.
In a distributed model, references are created independently in separate clones and must be reconciled when repositories synchronize: if two clones bind the same tag name to different commits, the protocol cannot preserve both bindings without violating name uniqueness.
Git therefore treats tags as mutable refs, prioritizing distributed flexibility over protocol-level immutability of release labels.
Platform-level mechanisms can partially compensate (\Cref{subsec:tags-disc-practical}), but they operate outside the core Git protocol and do not extend to plain Git operations or to other forges.

\subsection{Local and Remote Repository Synchronization}
\label{subsec:bg-local-remote-synchronization}

Git synchronization is built around exchanging objects and updating references.
When a developer pushes, the remote repository receives objects that it does not already have and updates one or more refs.
When another developer pulls, their local clone fetches the remote objects and updates local views of the corresponding remote refs.

In the common append-only case, synchronization is straightforward.
A branch advances from an old commit to a descendant commit; existing history remains reachable, and downstream clones can fast-forward.
The previous state is still present in the graph, and the new state extends it.

History rewriting breaks this simple model.
If a public branch is updated to point to a commit that is not a descendant of the previous branch tip, the remote ref has changed in a non-fast-forward way.
Downstream users who previously observed the old branch state may now hold commits that are no longer reachable from the public branch.
Users who clone after the rewrite may never see those commits at all.
% Figure~\ref{fig:bg-sync-rewrite} contrasts the append-only and rewritten cases.
This is the practical setting in which repository mutability becomes observable and consequential.

\section{Mutability in Git}
\label{sec:bg-mutability-git}

The object--reference distinction above supports local experimentation, branch movement, and release correction, but creates ambiguity when mutable names are treated as stable identifiers.

\subsection{History Rewriting Mechanisms}
\label{subsec:bg-history-rewriting}

Git provides several mechanisms for rewriting recorded history.
The \texttt{commit --amend} operation creates a replacement for a recent commit, often to modify the commit message, adjust metadata, or add forgotten file changes; \Cref{lst:commit-amend-message} illustrates correcting a typo in the most recent commit message.
Rebase operations replay, reorder, squash, split, or otherwise transform a sequence of commits.
These operations are common in local or work-in-progress development because they help developers prepare a cleaner sequence of commits before sharing it.

\begin{lstlisting}[
  style=thesisbash,
  caption={Correcting a typo in the latest commit message with \texttt{git commit --amend}.},
  label={lst:commit-amend-message},
]
# The latest commit message contains a typo ("authentcation").
$ git commit --amend -m "Fix authentication logic"
[main 7f3a1c2] Fix authentication logic
 Date: Mon Jun 1 10:00:00 2025 +0200
 1 file changed, 0 insertions(+), 0 deletions(-)
$ git push --force
 Enumerating objects: ...
 [...]
 To github.com:something.git
  + 9fddc2f...7f3a1c2 main -> main (forced update)
\end{lstlisting}

At the object level, rewriting does not mutate an existing commit object in place.
Instead, Git creates new commit objects.
The old commits remain in object storage as long as they are retained locally or by another archive, but they may become unreachable from the public refs of the repository.
Because commit identifiers cover parent links, a direct change to one commit can propagate to descendants: later commits that point to the modified commit must also be replaced by new commits.
The thesis describes this phenomenon as a snowball effect, where one direct modification can cause many reachable commit identifiers to disappear from a later public snapshot.

History rewriting is therefore not inherently suspicious.
It is a normal part of some development workflows, particularly for pull-request branches and automated maintenance branches.
It becomes problematic when performed on public branches consumed as external artifacts (\Cref{sec:bg-software-supply-chain}), where rewrites can invalidate previously observed commit identifiers and complicate audit trails.

\subsection{Force Pushes and Reference Updates}
\label{subsec:bg-force-pushes-reference-updates}

Public history rewriting is usually made visible through reference updates.
A remote repository may reject non-fast-forward updates by default, but maintainers can often override this protection through force pushes or platform-specific settings.
A force push changes the public ref to point to a new commit even when that commit does not extend the previous public history.

The same principle applies to tags (\Cref{subsec:bg-branches-tags-references}).
Tag deletion, recreation, and force-update are often legitimate, for example when correcting a release mistake or cleaning a repository.
Git's own documentation nonetheless discourages reusing a published tag name: the \texttt{git-tag} manual recommends issuing a new version label (for example, ``X.1'') rather than force-updating ``X'', because two clones may then both claim ``version X'' while resolving to different commits, and Linus Torvalds argued as early as 2007 that silently overwriting an already fetched tag is a security problem that maintainers must announce explicitly rather than perform quietly~\cite{git_tag_retagging_docs,torvalds_retagging_2007}.
The security and reproducibility issue is therefore not that such operations are always malicious, but that the practice runs against documented guidance and that downstream tools may not record enough information to detect its consequences.

\section[Safety, Security, and Reproducibility of Repositories and the SSC]{Safety, Security, and Reproducibility of Repositories and the Supply Chain}
\label{sec:bg-safety-security}

The mutability mechanisms of \Cref{sec:bg-mutability-git} can compromise distinct properties depending on who triggers them and why.
This section names those properties, states what it means to improve them for a repository and for the supply chain.

\subsection{Safety, Security, and Reproducibility}
\label{subsec:bg-triad}

This thesis separates three properties that repository and supply-chain mutability can compromise.

\emph{Safety} concerns protection against non-adversarial failures: accidental data loss, broken availability of a previously published state, and irreproducible builds caused by inputs that silently change.
A repository or supply chain is \emph{safer} when previously published states remain retrievable and unambiguous, so that honest mistakes and ordinary maintenance do not strand downstream consumers.

\emph{Security} concerns protection against a malicious actor who deliberately manipulates repository state.
It covers \emph{integrity}---a published reference must keep designating the source state a consumer verified---and \emph{confidentiality}---material that must stay private, such as credentials, must not leak through the published tree.
A repository or supply chain is \emph{more secure} when an adversary cannot retarget a trusted reference, rewrite a consumed history, or extract secret material without detection.

\emph{Reproducibility} is the safety-side requirement that a recorded build input continues to identify the same source artifact over time; it underpins auditing and reproducible builds~\cite{DBLP:journals/software/LambZ22}.
Recording a mutable name in place of a content commitment does not establish that guarantee: reproducibility may still hold in practice, but only as long as the reference is not altered.

The same operation can sit on either side of the safety/security line depending on intent, which is unobservable from archival facts alone: a reference update may be a benign release correction (a safety event) or a deliberate supply-chain attack (a security event).
The thesis therefore measures observable effects rather than intent, and treats mutability as a supply-chain integrity problem under the three conditions stated in \Cref{subsec:bg-trust-dependencies}.

\subsection{Stable References and Downstream Dependency Resolution}
\label{subsec:bg-stable-references-dependency-resolution}

Downstream tooling consumes repository references in many ways.
Package ecosystems and build systems translate repository states into consumable artifacts: they may fetch source archives from forges, clone repositories, resolve tags, apply patches, check integrity metadata, and produce binary packages.
The reliability of that pipeline depends on assumptions about the upstream references recorded as inputs.
Some package ecosystems support direct dependencies on Git repositories.
Build scripts may fetch source archives generated from tag names.
Continuous integration workflows may use third-party actions or tools by specifying a tag.
In all these cases, the repository reference becomes part of a larger software supply chain.

If a dependency specification records a commit identifier, the source identity is stable as long as the object remains available.
In that case, integrity is guarented but availability might still be an issue.
If it records a tag name, stability and integrity depend on whether the tag is preserved, deleted, or updated.
A deleted tag can cause a fetch failure.
A updated tag can cause the fetch to succeed while producing a different source state.
The second case is more subtle because the dependency name still resolves.

This distinction is visible in package managers that record integrity metadata.
Nix, for example, stores expected hashes for fixed-output sources.
If a tag later resolves to different content, the build does not silently accept the new source; it fails with a hash mismatch.
This behavior avoids silent substitution, but it also shows that tag mutability can become an availability and rebuildability problem.
A package that was reproducible while a cached source artifact was available may become unrebuildable later if rebuilding requires fetching a tag that no longer matches the recorded hash.

\subsection{Implications for Reproducible Builds}
\label{subsec:bg-provenance-reproducible-builds}

Reproducible builds aim to increase confidence that generated binaries correspond to auditable source code~\cite{DBLP:journals/software/LambZ22}.
That goal depends on stable identification of build inputs, not only on deterministic build processes: if an input is named by a mutable ref, a deterministic process may still fail to reproduce the same artifact because the resolved source tree has changed.
Build-relevant resolution therefore requires pinning to a commit hash or to an independently archived persistent identifier~\cite{cise-2020-doi}; human-readable release names remain useful for communication but do not by themselves establish provenance.

\subsection{Secrets in Source Code Repositories}
\label{subsec:bg-secrets}

The confidentiality side of security has a recurring failure mode in public repositories.
That distribution model (\Cref{sec:bg-software-supply-chain}) assumes the published tree is safe to inspect, clone, and reuse.
When authentication material is committed by mistake, the repository becomes an accidental channel for credential exposure.
In this thesis, a \emph{secret} denotes any credential or key material whose disclosure would grant access to a protected resource: API tokens, passwords, database connection strings, private keys, certificates, and similar values that should remain outside version control.

The weakness is well known in software security practice.
Hard-coded credentials are catalogued as CWE-798~\footnote{https://cwe.mitre.org/data/definitions/798.html} and recur among the most consequential classes of software defect.
Empirical work on public GitHub repositories shows that leakage is systematic rather than anecdotal: Meli et al.\ recovered more than \num{200}\,k API keys and tokens embedded directly in source code~\cite{DBLP:conf/ndss/MeliMR19}, and industry monitoring reports describe millions of exposed credentials in public repositories in a single year~\cite{segura2022secrets}.
Sinha et al.\ argued early that version control systems should incorporate automated mechanisms to prevent such leaks and to assist developers after exposure~\cite{DBLP:conf/msr/SinhaSDPM15}.
Because public repositories are copied, forked, indexed, and archived, a single push can propagate sensitive values far beyond the maintainer's immediate workspace.

\subsubsection{Detection and Prevention}
\label{subsec:bg-secrets-detection}

Two complementary lines of defence address credential exposure in repositories.
The first is \emph{detection}: scanning repository contents for patterns that resemble known secret formats.
Open-source tools such as gitleaks and TruffleHog implement large rule sets over file contents; benchmark studies show that their reported findings overlap only partially, meaning that, so far, no single detector captures the full set of machine-recognisable secrets~\cite{DBLP:conf/msr/BasakNRW23,DBLP:conf/esem/BasakCRW23}.
The second is \emph{prevention at the forge}: hosting platforms can scan pushes, warn maintainers, notify credential providers, or block known-dangerous formats before they become part of the public history.
GitHub, for example, rejects pushes that contain certain private-key formats and operates secret-scanning partnerships with major providers.

These mechanisms reduce risk but do not eliminate it.
Detector coverage depends on the rule set, the file types scanned, and whether credentials are split, encoded, or stored under unusual paths.
Platform scanning applies only to the forge that receives the push and to the credential families for which an integration exists.
Private keys for self-hosted services, database passwords, certificates, and values copied into archives or mirrors may fall outside the cleanest version of this model.
Filename heuristics---matching paths such as \texttt{.env}, \texttt{id\_rsa}, or \texttt{credentials.json}---are therefore widely used in practice as a coarse first filter before content scanning, including in the empirical work of this thesis (\Cref{chap:histories,chap:secrets}).

\subsubsection{Recommended Remediation}
\label{subsec:bg-secrets-remediation}

Surveys of secret-management practice converge on a clear hierarchy.
Credentials should be kept out of source entirely, through environment variables, secret managers, and short-lived tokens that can be rotated without rewriting history~\cite{DBLP:conf/secdev/BasakNRW22,DBLP:journals/corr/abs-2211-06213}.
When exposure occurs despite these precautions, the security remediation is to invalidate the leaked value: revoke the token, replace the key, reset the password, or otherwise remove the authority that the exposed string grants.
Krause et al.\ study how developers prevent and respond to accidental commits; their findings reinforce that rotation, not deletion from the repository alone, closes the security gap~\cite{DBLP:journals/corr/abs-2211-06213}.

History rewriting is nonetheless a common cleanup action after a leak.
Maintainers can amend or rebase recent commits, run history-filtering tools over past trees, and force-push the rewritten branch so that the current public view no longer contains the offending file (\Cref{subsec:bg-history-rewriting,subsec:bg-force-pushes-reference-updates}).
This action can reduce the chance that a future clone or casual inspection rediscovers the value, and it may satisfy organisational policy about what may remain in advertised project history.
It does not, however, act on the credential itself.
Nor does it erase every copy of the exposed commits: forks, local clones, search indexes, and independent archives may retain the pre-rewrite state long after the upstream repository looks clean (\Cref{sec:bg-software-heritage}).
The distinction between repository-level cleanup and credential-level remediation is central to the secret-removal thread of this thesis.

\section{Software Heritage: an Archival Model for Source Code}
\label{sec:bg-software-heritage}

The empirical contributions rely on an archival view of public repositories because, after a ref update or history rewrite, the previous public state may no longer be available from the original forge (\Cref{sec:bg-mutability-git}).
Without an independent archive, the evidence needed to compare before and after states may have disappeared.

Software Heritage is a universal archive of publicly available source code~\cite{swhcacm2018,swh-msr-2020-challenge}.
It periodically visits software \emph{origins}---typically repository URLs, analogous to the repositories discussed above---and stores each observed state as a \emph{snapshot}.
For Git repositories, a snapshot records visible references and the archived objects designated by those references.
Software Heritage stores these artifacts in a global Merkle DAG and assigns persistent identifiers (SWHIDs) to each archived object~\cite{cise-2020-doi}.
The archive uses its own type names, but the mapping from Git is direct for the object types this thesis relies on: a \emph{revision} corresponds to a commit, a \emph{directory} to a tree, and a \emph{content} object to a blob; SWHIDs also identify \emph{releases} (annotated tags) and snapshots themselves.
Unlike a forge, which exposes only the current state of a repository, the archive retains every state it has observed, and SWHIDs are content-derived, so the same identifier always refers to the same artifact regardless of when or where it is retrieved~\cite{iso-swhid} (Figure~\ref{fig:bg-swh-architecture}).

\section{What Software Heritage Brings, and What New Threats It Reveals}
\label{sec:bg-swh-implications}

The archival model turns repository mutability from an ephemeral event into a measurable one, but it also exposes consequences that the forge view hides.

\subsection{Observability of Mutability at Scale}
\label{subsec:bg-swh-observability}

Because Software Heritage retains successive states of the same origin, comparing two consecutive snapshots reveals which references existed in both, which changed target, and which appeared or disappeared.
In the altered-histories contribution, consecutive snapshots of the same origin are compared to detect commits that were reachable in an earlier snapshot but missing from a later one.
In the tag-alterations contribution, the same comparison is applied to release tags (\Cref{subsec:bg-tag-alterations}).
In both cases, the archive preserves evidence of states that may no longer be visible in the current upstream repository.
This before-and-after observability is what makes the measurements in this thesis possible, and it directly serves supply-chain safety and security: it lets a consumer or auditor establish what a reference designated when it was trusted, even after the forge has overwritten it.

This observability also explains why some mutability is hard to detect from the forge alone.
Rewritten histories may go unnoticed by users who perform fresh clones, because they see only the current public state.
Users who previously cloned the repository may detect disruption when pulling, but many automated workflows do not preserve such state.
As a result, repository history can change in ways that are difficult for downstream systems to observe unless they rely on external archives or dedicated monitoring tools.

The archival view also imposes limits.
It can only observe alterations that occur between visits and remain visible long enough to be captured.
If a reference is changed and restored between two archival visits, the alteration may be missed.
If several changes happen between two visits, they may be observed as one aggregate transition.
Software Heritage also does not visit every origin at the same rate: a scheduling heuristic prioritises more active origins for more frequent snapshots, so popular and heavily maintained repositories tend to be observed more often than dormant ones.
That uneven coverage can bias prevalence estimates, because alterations in rarely visited origins are easier to miss, but the bias is not uniformly harmful for a supply-chain reading of the results: widely used repositories are both sampled more densely and disproportionately likely to matter as attack targets or as source states that downstream consumers actually rebuild.
Counts derived from such snapshots should therefore be interpreted as lower bounds on observable alterations, not as complete records of every repository event.

\subsection{Tag Alterations}
\label{subsec:bg-tag-alterations}

For this thesis, a \emph{tag alteration} is an observable change in what a tag reference designates between two snapshots of the same origin.
The tag-alterations contribution distinguishes two main cases.
A \emph{tag move} occurs when a tag is present in both snapshots but resolves to a different target, including deletion followed by later recreation with a different target.
A \emph{tag deletion} occurs when a tag present in an earlier snapshot is absent from a later one.
Moves and deletions differ in observability: a deletion breaks resolution, whereas a move preserves the tag name while changing the retrieved object (\Cref{subsec:bg-stable-references-dependency-resolution}).
